## Method

1. **Extraction** (`evals/extract_full.py`): for each case we take exactly the documents its flow references (each answer node carries a `doc` index), concatenated.

2. **Question mapping** (`qid → catalog entry`): each answer node carries a `questions` map from question id to catalog index. This gives the exact instruction text and answer type (noul / score / choice) for every question — verified 100% coverage, no positional guessing.

3. **Reference**: the published consensus — mean of GPT-6 Astra (high thinking) and Claude Fable 5.1 (high), averaged per question. A model "agrees" when its final answer (argmax for probabilities) equals the consensus argmax.

4. **Answerers compared**:
   - **opus / sol / typesafe (Jev)** — their published answers, as shipped in the viewer data.
   - **deepseek-v4.1-flash** — subagent calls on the session model (`opencode-go`, variant `max`), one prompt per workflow (invoice split per case), all questions asked at once. Total cost ≈ **$0.10**.
   - **local-qwen3-8b** — Qwen3-8B-4bit through the parallel-constrained-decisions engine (MLX, M5 MacBook Air 16 GB), one batched pass per case, all questions as schema fields.

5. **Scoring** ([`evals/score_full.py`](../evals/score_full.py), workflow-intersection logic): per-workflow and overall agreement, plus **workflow-specific common subsets**. Within each workflow, intersect the answered pairs of models with at least one answer in that workflow; models with zero answers are excluded from that intersection. Qwen3-8B has no invoice answers, so invoice's intersection excludes it. The aggregated denominators therefore differ: 343 for models covering all four workflows, 160 for Qwen3-8B. This is not one global subset answered by every model.

## What this means (the honest reading)

1. **The local engine is ~13 points behind Jev on Jev's own benchmark** (73.8% vs 86.6% on the
   strict common subset). The earlier 5-case read (`11-...`) that the local model "ties Jev" was an
   artifact of the tiny curated sample. On the full public set it does not tie.
2. **The frontier models cluster at 86–90%** against their own consensus; Jev lives in that cluster
   (86.6%) despite being two orders of magnitude cheaper. That is the real achievement.
3. **The free local model is not accuracy-competitive, but it is free, private, and offline.**
   73.8% on this suite is far above the majority-class baselines (51–64% per-type, 64–88% per-question)
   but far below the frontier cluster.
4. **The 8B run outscored the 7B on their three shared workflows.** On those same
   160 common pairs: Qwen3-8B **114/160 (71.2%)**, Qwen2.5-7B **105/160 (65.6%)**,
   Jev **129/160 (80.6%)**. The 8B gap to Jev is **9.4 percentage points** here,
   not ~15 points obtained by mixing three- and four-workflow totals. Different
   model families also mean this comparison does not isolate model size.
5. **Where the local model is strong:** Security Incidents curated cases (19/26 for the 8B — the
   best local result, close to Jev's 20/26) and the majority of invoice questions (148/183 = 80.9%,
   though that column is "easy" — the per-question majority baseline is 88%).
6. **Where it is weak:** customer service (59/85 = 69%) and agent-trace attribution/intent questions —
   the multi-document, multi-hop cases.

## Baselines

Per-type majority (answer the most frequent reference value for that type): 49–64%.
Per-question majority (where the question appears ≥2 times): 64–88%.
The invoice column's high per-question majority (88.0%) means a large share of its 184 questions have
one dominant answer — read that column with that in mind.

## Interpretation rules (pre-registered before seeing the numbers)

- The reference is a **two-model consensus**, not ground truth. Agreement measures "how close to the frontier average", not correctness.
- These 20 cases are the **curated public subset** — the viewer chose them because they are interesting (disagreements, edge cases), so absolute levels are not comparable to TypeSafe's published per-workflow averages.
- Coverage differences are reported, not hidden: a model that answers 40/373 pairs and gets 80% is not comparable to one that answers 373 and gets 70%. Compare common-subset cells within the same workflows; the table's /160 and /343 overall totals are not directly comparable.
- Single run, no sampling variance, n=20 cases. This is a real but small benchmark; the write-up says so.

## Known local-engine limitations exposed by this eval

> **Superseded in part by the addendum at the end of this file.** The collision
> characterisation here counted options sharing a first *character* (89 questions);
> the exact token-level rule finds 26 slots in 8 fields, and the second bullet's
> cost estimate is now handled automatically by the package (measured cache growth,
> a RAM-clamped budget, and chunk-size halving on failure).

1. **Choice-option collisions.** 89 of the choice questions in this suite have options that
   share a first character (e.g. `credit_or_discount` vs `charge_on_top`, `plausible` vs `unconfirmable_story`),
   which triggers the engine's sequential collision-resolution path — slower and with a synthesized
   confidence rather than a true softmax. Affects invoice + customer_service + agent_trace choice fields.
   (At the token level the real figure is 26 slots in 8 fields; see the addendum.)
2. **Memory cost of many-field schemas.** The engine broadcasts the KV cache once per field. Invoice
   cases (48 fields over ~8.5k-token inputs) do not fit on a 16 GB machine in one pass: they require
   chunking (we used 6 fields per chunk, ~55 s per chunk, ≈7 min per case for the 7B).
   The 8B model, with twice the KV size per token, was roughly 4x slower on the same cases.
3. **Prefill dominates long contexts.** For the largest agent-trace case (44.7k chars), prefill alone was
   37–46 s; the parallel pass is a small fraction of total time at long context.

These are honest costs of running this decoding pattern locally, and they are why the local model's
agreement is lower than the API models' — not because the questions were unanswerable.

## Addendum (2026-09-16, later): where the 73.8% actually comes from

A slice analysis of the local run changes how the total should be read. Its report
and generator exist in the separate local research checkout, **not this public
mirror**; see [Evidence provenance](#evidence-provenance-local-artifacts-checked-2026-09-17)
for exact paths and content hashes. The report identifies the recorded 373-pair
MLX 7B run and cross-checks 273/373 against the stored summary. Findings below
are reported by that existing analysis; this docs audit did not rerun its tokenizer
or model analysis.

- **`noul` questions look strong and are not.** 83.1% overall, but the true rate is
  18.6%, and a constant "false" scores 92.7% on invoice questions. The model finds
  0 of 8 positives there. Overall, accuracy is 51.5% for a constant answer and 73.2%
  for the model — real signal, concentrated in agent-trace (balanced accuracy 70.3%)
  and customer service (64.5%).
- **Score questions (0–3) are the weakest type: 7/27 exact, 85.2% within one level.**
  Every score slice scores *below* its constant baseline. The runner also hardcoded a
  4-level schema for the 10 published score questions that define five levels, so
  level 4 was unreachable for those — 2 reference answers were unwinnable.
- **Choice questions: 63.6%, dominated by listing order.** The model picks the first
  listed option in 82% of slots and is right 96.7% of the time when the truth is
  listed first versus 24.5% when it is not.
- **The collision question is settled, and not in the direction the old caveat above
  suggests.** Only 26 of 110 choice slots sit in token-colliding fields (not 89 —
  that figure counted options sharing a first *character*). Their raw accuracy is
  +7.3 pp above non-colliding fields, which is a listing-order artifact: stratifying
  by where the truth sits in the option list moves the gap to −0.2 pp. Zero errors
  were same-token sibling confusions.
- **3 slots are mechanically unanswerable**: the reference answer is not among the
  options the runner offered.
- **31 of 81 fields that appear ≥3 times give a constant answer while the truth
  varies.** The failure mode is "ignores the case", which is a training problem
  rather than a decoding one — hence the LoRA interest in Phase 5.

None of this changes the headline: 73.8% on the strict common subset, ~13 points
behind Jev. It does change the interpretation — the model is reliable where the
answer is written down, and near-useless where it must be inferred or counted.

**A separate packaged-path record covers 277 slots, not the 343-pair common
subset.** The existing local calibration JSONL contains **196/277 correct (70.8%)**;
all 277 `(workflow, case_id, qid)` keys are unique and each stored `correct` flag
matches `chosen == target`. **One stored target disagrees with the source
consensus:** `agent_trace_observability / trace_9222e1c90cfe97d34a6893f13889ff1d /
expressed_satisfaction` has source target **`4`**, packaged target **`3`**, and
packaged chosen answer **`4`** (stored as incorrect). All other targets match.
Scoring these same recorded choices against the source consensus therefore gives
**197/277 (71.1%)**, not 70.8%. The latter is verified only as the packaged
records' stored-label score, **not** as agreement with the original consensus.
This is an arithmetic correction using existing artifacts, not a new model run;
the raw files have not been changed. Its workflow coverage is Security **48**, AgentTrace
**49**, Invoice **91**, CustomerSvc **89**. Comparing the stored choices with the
